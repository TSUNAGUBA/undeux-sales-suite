# UndeuxSales 売上参照スイート

小売（取引先）から週次で提供される売上参照データを PostgreSQL に格納し、
売上を可視化する Web アプリケーション。

分析画面は分析用ディメンショナルモデル（`mart` スキーマ＝スタースキーマ。設計: `docs/star-schema-design.md`）
から集計する `/mart` 配下のページ群（プロトタイプ段階の旧分析ページは廃止済み）。

ナビゲーションは目的別ドリルダウン構成（メニュー定義の SoT: `frontend/app/utils/navigation.ts`）。
`/`（ホーム）で目的カテゴリを選び、配下ページをタブで切り替える。表示メニューは**アカウント種別**で出し分ける（後述）。

- **OTB管理**（バイヤー＝小売のみ） — 全社OTBサマリー
- **全体モニタリング**（サプライヤー＝メーカー） — 全社サマリー／売上分析
- **在庫マネジメント**（サプライヤー） — アクション駆動の在庫管理
- **アイテム分析**（サプライヤー／バイヤー） — 商品別分析／商品詳細分析／写真帳／週間モニタリング／日次分析：特定品番／ブランド・シリーズ分析／商品導入管理（メーカー向けを小売にも配下タブごと移植）
- **副資材チェック**（サプライヤーのみ） — 指示書（工程表FAX等）とタグ画像をAIで突合し、レイアウト・順番・内容を検品する独立メニュー
- **店舗分析**（バイヤー＝小売のみ） — 店舗別売れ筋ランキング（発注タイプ・店舗属性・商品属性の条件で集計。店舗粒度の属性・発注区分は現状データが無いためモック）
- **AIチャット**（サプライヤー／バイヤー） — 業務チャット／商談チャット／RAG設定（ナレッジ管理）
- **データ管理** — 予算管理／商品マスタ／週次取込／業態・部門マスタ（商品マスタ・週次取込はサプライヤーのみ）
- **探索・予測分析** — クロス集計／部門分析／ランキング分析／散布図・回帰分析／重回帰シミュレーター／意思決定オントロジー・ビュー

> ホーム（`/`）はサプライヤー向けに、全社サマリーのカード型KPIと「今週のインサイト & おすすめ」
> （今週の急上昇アイテム TOP3・全社売上の予算達成率メーター。所見はルールベースで自動生成）を
> ダッシュボードとして表示し、その下に目的別メニューを並べる。
> メニューの並びは 全体モニタリング → 在庫マネジメント → アイテム分析 → 副資材チェック → データ管理 → 探索・予測分析。
> 旧「週間モニタリング」「ブランド/シリーズ分析」はアイテム分析配下のタブへ統合した（URL は不変）。

### アカウント種別（サプライヤー／バイヤー）

利用者は **サプライヤー（メーカー）** と **バイヤー（小売）** のいずれかのアカウント種別を持つ
（Firebase カスタムクレーム `accountType`。未設定の既定は `supplier`）。種別はメニュー・タブ・ルートを出し分ける。

- **サプライヤー（メーカー）**: 自社の売上・在庫の管理/分析（既存の「売れた結果を見る」画面群）。
- **バイヤー（小売）**: 全サプライヤー横断で仕入予算・OTB（Open To Buy＝仕入枠）を管理し、「未来の仕入意思決定」を行う。

> **重要（運用上の制約）:**
> - 現状のロール出し分けは**ナビゲーション/画面レベル**であり、バックエンドのデータ分離（メーカーは自社商品のみ）は
>   マルチベンダ対応として後続。**セキュリティ境界ではない**（API はトークンが有効なら現状すべてのデータを返す）。
> - 開発/デモ用にヘッダーでアカウント種別を手動切替できる（localStorage 上書き）。実運用ではクレームを SoT とする。

- **全社OTBサマリー**（`/mart/otb`・バイヤー向け） — 「未来の仕入意思決定」をする OTB（Open To Buy）ダッシュボード。OTB残高・利用率・発注残・予測月末在庫・WOS・欠品/過剰SKU数・平均リードタイム等のKPI、強み/弱み/機会/リスク、今週の推奨アクション、OTB構成ウォーターフォール、週次推移、カテゴリ別OTBランキング、発注残分析（未出荷/輸送中/検収済）、AIコメントを表示。**現状は数値・所見をルールベースで生成するモック**（AI本格導入は後続。SoT: `frontend/app/utils/otbMock.ts`）。色は青=OTB・発注余力／緑=健全／黄=注意／赤=欠品・過剰在庫・納期遅延。目標売上・仕入予算は予算管理の登録値を反映
- **全社サマリー**（`/mart`） — AIレポート風の経営サマリー。業態タブ＋部門チップ（各「すべて」）で絞り込み、主要KPI（前年同月比つき＝締まった直近月と前年同月の比較）・週次トレンド・同月まで累計売上（当期 vs 前期の数量・金額をバーで比較）・「今週のアクション（在庫）」ダイジェスト・集計軸別の売上構成に加え、主要指標からルールベースで自動生成するエグゼクティブサマリー（要点＋強み/弱み/機会/リスク）を表示。要点・KPI の前年比は未来月度の混入で比較が歪むのを避け、締まった直近月×前年同月で算出。mart の再構築も実行可
- **売上分析**（`/mart/sales`） — 週次売上推移グラフ（売上数量/売上金額=折れ線、店頭在庫=棒、気温=折れ線）・週次明細。期間（年月 from-to）はフィルターの最上部に配置。売上金額ランキング・順位変動・部門別売上ランキングは目的が薄いため除外し、ランキング系はランキング分析へ集約
- **週間モニタリング**（`/mart/weekly`） — 直近取込週の実績と前週比（WoW）、週次推移グラフ・前週比つき週次明細
- **商品別分析**（`/mart/products`） — 画像カードの商品一覧。フィルターは全社サマリー踏襲（業態・部門・年度・季節・棚割1・平均在庫日数）＋ブランド・担当者・キーワード。カード押下で商品の詳細分析（画像・基本情報・サマリー・SKU情報・週次売上推移グラフ）へ（クロス集計は専用ページ `/mart/crosstab` に集約し、詳細分析からは当該商品のスコープを引き継いで遷移）
- **商品詳細分析**（`/mart/item-detail`） — SKU（品番3桁×単品4桁）単位の「売数／在庫数／在日／販売価格／気温（東京・札幌・沖縄）」を週別（週を列展開）／当週（売上参照ファイル準拠）で分析。当週は売数に加え日別内訳（月〜日・当週売数を決定的に按分したモック）と前週〜4週前の週次売数を併記。行区分は表示/非表示を切替でき最終状態を localStorage に保存。表は「品番/単品」と「品名/カラー/サイズ」の間に「商品記号/棚割1/棚割2」列を追加し、SKU グループ間に罫線。週別表は左メタ列＋区分列を横スクロール時に左固定。在日の色分け（〜30赤／31-60青／61〜既定）・値下げ週のセル強調・消化率分解・表示範囲サマリー・Excel 貼り付け用コピーを提供。フィルターは業態・部門／品名（スペース/カンマ区切りの AND 部分一致）／商品記号（部分一致）／品番3桁／棚割1・棚割2（部分一致）／期間。棚割はレスポンス未提供のため現状モック値（SoT は集計素材）
- **写真帳**（`/mart/photobook`） — 商品を投入企画書レイアウトのスペックシート（品番・品名・PB・素材・上代・画像・サイズ／カラー・投入日・受注日・先付 等）で一覧。商品マスタに無い項目は空白。画像は全カード同一の固定高さ（object-cover）で揃えて表示。1〜4アイテムを選択して Excel（.xlsx）出力可（出力は投入企画書レイアウト＝1商品7列×最大4ブロック横並び・結合セル/罫線・サイズ数量マトリクスは「計」を SUM 数式で自動集計。各商品の主画像は画像枠に高さ優先で枠内に収めて添付＝PNG/JPEG。取得失敗時は画像なしで出力）。フィルターは業態・部門／品名（部分一致）／商品記号（部分一致）／品番3桁
- **在庫マネジメント**（`/mart/inventory`） — アクション駆動の在庫管理。ページ内6タブ（ダッシュボード／在庫一覧／滞留在庫／不動在庫／残在庫／帳票区分、`?tab=` で直リンク可）。滞留（在庫日数60日超×消化率75%未満）・不動（直近8週出荷ゼロ）を SKU 単位で自動抽出し、「今週のアクション」フィード・推奨アクション（発注抑制／値下げ候補／売場再点検／処分検討／経過観察）・商品記号ポジショニング4象限（凡例非表示・マウスオーバーで商品記号を表示。商品記号=LG{部門}{連番}を単位に集計＝上部フィルターの業態・部門で絞込。モック）・在庫鮮度帯・在庫金額（原価）を提供。**残在庫**は数量①〜⑬（①先付〜⑤店頭在庫=売上参照／⑥発注済未納品・⑨〜⑬=算出／⑦取置・⑧論理在庫=WMS）を業態/部門/商品記号＋帳票区分（売発注・情報発注の複数選択・既定は両方）で絞り表示（倉庫系はモック）、**帳票区分**は SKU の売発注／情報発注／無の週次変化を「売→情」等の略記で表示し、変化種別の複数選択フィルタ（既定は全表示）と履歴モーダルを提供（モック）。閾値の SoT はバックエンド `InventoryHealthRules`（適用値は API レスポンスで返却）
- **ブランド/シリーズ分析**（`/mart/brand`） — ブランド軸・シリーズ（商品記号）軸の売上ランキング・構成比（指標: 売上金額／数量／粗利。シリーズはデータに無いため商品記号で代替）
- **クロス集計**（`/mart/crosstab`） — 行×列の2軸マトリクス（複数集計値の表示モード3種・行列スワップ・気温オーバーレイ・Excel貼り付け用クリップボードコピー）。各分析ページに散在していたクロス集計をここへ集約し、商品詳細分析・在庫マネジメント・ランキング分析からは条件を引き継いでドリルダウンする。集計軸・メトリクスの定義は `frontend/app/utils/crosstabCatalog.ts` を SoT として共有
- **部門分析**（`/mart/department`） — 「部門」を主軸にした売上・数量・粗利の分析。部門別ランキング（棒・明細表）・KPI（対象部門数を含む）に加え、二次軸（業態・季節・年・四半期・月 等）を切り替えた「部門 × 任意軸」のクロス集計を1画面に集約（`BarChartCard`／`DataTable`／`CrossTabTable` を再利用）。フィルターは全社標準（業態・部門・年度・季節・棚割1・平均在庫日数）
- **ランキング分析**（`/mart/ranking`） — 単軸ランキングに「複合スコアリング」「期間比較・順位変動」「ABC/パレート分析」の3レンズを統合。全集計軸で「店頭在庫数」「直近在日（在庫日数の近似＝店頭在庫÷期間平均日販）」を併記し、商品記号別では「残在庫数（倉庫在庫・モック）」「残在庫金額（原価）」も併記
- **散布図・回帰分析**（`/mart/scatter`） — 「気温×売上数量」の単回帰でスイッチ温度を、「消化率×値引き率」の4象限＋型番別明細で値下げ判断を可視化
- **重回帰シミュレーター**（`/mart/simulation`） — 気温・前週売上・値引き率のスライダーで売上・粗利をリアルタイム予測（裏側は重回帰＋価格弾力性）
- **意思決定オントロジー・ビュー**（`/mart/decision`） — 滞留SKUを「意味／関連／アクション＆制約」の3次元で捉え、制約（✗）で潰れず残った打ち手（○/△）だけを意思決定選択肢カード（A/B/C・AI推奨）へ昇格させる意思決定支援ビュー。目的関数・打ち手・選択肢はヘッダーのアカウント種別トグル（メーカー／小売）に連動。**概念モック（ダミーデータ固定・実データ接続／実行処理は次フェーズ。SoT: `frontend/app/utils/decisionOntologyMock.ts`）**
- **商品導入管理**（`/mart/introductions`） — 商品単位の導入日一覧。業態（タグ・複数選択）・部門・ブランド・服種・担当者・キーワード・導入時期/導入日 From-To で絞り込み
- **業務チャット**（`/ai/business-chat`） — 「システム部（Web-EDI・受発注）」「商品管理部（品質管理・品質規格）」「物流部（直流・納品・物流）」のいずれかを先に選び、蓄積ナレッジ（RAG）を根拠に AI が業務質問へ回答（出典明示・根拠がなければ相談窓口を案内）。SSE ストリーミング応答。**要 AI 設定（Vertex AI / Gemini。未設定時は「AI未設定」表示）**
- **商談チャット**（`/ai/negotiation-chat`） — 上部の業態 chips → 配下部門 chips で相手を選び、AI が当該業態×部門のしまむらバイヤーとして商談シミュレーション。蓄積ナレッジに加え、分析マート（スタースキーマ）から業態次元で決定的に集計した実績（週次実績・売上上位商品・在庫スナップショット）を根拠に応対する。**要 AI 設定（Vertex AI / Gemini）**
- **RAG設定**（`/ai/rag-settings`） — ナレッジ管理。運営者RAG設定（しまむらグループ／業態／部門／基本情報／マニュアル。編集は管理者のみ）とユーザーRAG設定（マニュアル以外）に分割。自由入力またはファイル（.txt/.md/.pdf/.jpg/.png）で登録し、原本を保管したままチャンク化・ベクター化（ローカル決定的埋め込み）・字句索引化して検索テストも可能。しまむら提供資料由来の初期ナレッジ27件を起動時に冪等シード（設計: `docs/design.md` §12）
- **業態・部門マスタ**（`/org-master`） — しまむらグループの業態×商品部（部署・連絡先・フロア）×部門の相関と相談受付デスクのマスタメンテナンス。初期データは「お取引の基準 総括編」由来で、修正は管理者のみ（修正はチャットのペルソナ・自動生成ナレッジへ即時反映）
- **予算管理**（`/mart/budget`） — 売上予算（両ロール）・仕入予算（バイヤーのみ）を年度×集計軸（全社／部門／業態）で登録。登録値は OTB サマリー等で活用。**永続化は当面ブラウザの localStorage（端末・ユーザー間で共有されない暫定実装。バックエンドの予算テーブル連携は後続）**
- **商品マスタ**（`/product-master`） — マスタ登録商品のカード一覧・詳細（データ管理）。詳細には付属情報（組成・原産国・洗濯表示・表示順序等。`m_product_attachment` 登録時のみ）を表示
- **副資材チェック**（`/subsidiary-check`・サプライヤーのみ） — 指示書（工程表）画像とタグ（下げ札・品質表示）画像をアップロードし、AI が**レイアウト／順番／内容**の3要素を比較チェック（判定: 合格／要確認／要修正）。商品マスタの付属情報が登録済みならチェックの元ネタとして突合。ページ内タブ（チェック履歴／新規チェック（画像）／**手入力チェック**／**手入力履歴**／**タグパターン設定**／ルールブック、`?tab=` で直リンク可）。AI チェックはバックグラウンドで実行され（結果は画面が自動更新）、記録・画像は PostgreSQL に永続化。再実行は失敗時・処理中断時のみ可能（確定済み判定は保護）。ルールブックはしまむら副資材規定（アイコン優先順位・禁止用語・表示順序・寸法）のカタログ。**手入力チェック**は、タグパターンで構成したフォームに表示項目（品番・組成・洗濯表示アイコン等）を手入力し、アップロードしたタグ画像から AI が読み取った内容と**項目単位で突合**（文字列／組成割合／洗濯アイコン列＝並び順も検査）。洗濯アイコンは自己完結のインライン SVG マスタ（`CareIconCatalog`）。**要 AI 設定（Vertex AI / Gemini。未設定時は 503「AI未設定」）**（設計: `docs/design.md` §13）
- **週次取込**（`/imports`） — 週次CSVのアップロード取込と取込履歴

フィルタは「フィルタ → 集計単位 → 表示集計値」の導線で統一。業態・部門は全社サマリーを標準とした
タグ（`ScopeFilterTags`・複数選択。表記は業態 `{コード}: {名称}({略称})`／部門 `{コード}: {名称}`）で
共通実装し、共通フィルタに **棚割1** と **平均在庫日数（在日）**（◎30日以内／〇31〜60日／△61日以上）を持つ。
気温は `db/climate_daily.csv`（東京/札幌/那覇の日次実測）を `mart.dim_climate` に投入して用い、
CSV 未カバーの週は標準気候（気象庁平年値ベースのサンプルデータ。標準＝東京・寒冷＝札幌・温暖＝那覇）へ
フォールバックする。mart は `sales_weekly`（取込ソース層・SoT）＋商品マスタから再構築する派生キャッシュで、
帳票区分・棚割は集計軸としては未対応（棚割1はフィルタ対応済み）。

横スクロールする表（ランキング・残在庫・帳票区分・商品詳細分析・クロス集計・在庫一覧・週次/日次明細・
配下SKU 等）は、識別列（順位・商品記号・品番/単品・名称等）とステータス列までを左端に固定し、数量・指標列だけを
横スクロールさせる。共通表 `DataTable` は列定義の `frozen`（＋複数固定時は `width`）で固定列を宣言でき、
固定ヘッダ z-30 ＞ 上部固定ヘッダ z-20 ＞ 固定ボディ z-10 ＞ 通常セル の z-index 規約で重なりを制御する。

## クイックスタート（Docker Compose）

```bash
# 1. 環境変数を用意（Firebase 設定を記入）
cp .env.example .env

# 2. 起動（DB 構築 → 初期データ投入 → API → フロントエンド）
docker compose up --build
```

| サービス | URL |
|---------|-----|
| フロントエンド | http://localhost:3000 |
| API | http://localhost:8080 |
| API ドキュメント（Swagger） | http://localhost:8080/swagger |

初回起動時、`reference/` の初期DBダンプ（約160万行）が自動投入される（数分かかる場合がある）。

> **ログインには Firebase の設定が必要です。** Firebase コンソールでプロジェクトを作成し、
> Authentication（メール/パスワード）を有効化のうえ、`.env` に各値を設定してください。
> 未設定でもアプリは起動しますが、ログインはできません。

## ローカル開発

### バックエンド

```bash
cd backend
dotnet test                              # ユニット・統合テスト（PostgreSQL が必要）
dotnet run --project src/UndeuxSales.Api  # API 単体起動
```

統合テストは PostgreSQL（既定 `localhost:5432`、ユーザー/パスワード `undeux`）に接続し、
テスト用DB `undeux_test` を自動作成する。

### フロントエンド

```bash
cd frontend
npm install
npm run dev        # 開発サーバー（http://localhost:3000）
npm run generate   # 静的SPAを生成（.output/public）
npm run typecheck  # 型チェック
```

## 週次CSV取込フォーマット

- 文字コード **UTF-8**、1行目はヘッダー（列名）。
- `import_date` は **月曜日**（取込日。前週 月〜日のデータを表す）。
- 必須列: `import_date, customer_code, gyotai_code, chohyo_kubun_name, department,
  hinban_code, tanpin_code, hinmei, shohin_kigou, color, size,
  toshu_uriage_count1`〜`7, uriage_count_zenshu, uriage_count_2shumae`〜`4shumae,
  zaikosu, ruikei_uriage_count, ruikei_nohin_count, hatchu_count, donyu_date,
  zainiti, genka, baika, kisetsu, sakizuke_count`（任意列: `tanawari1, tanawari2`）。
- アプリの「週次取込」画面からテンプレートCSVをダウンロードできる。
- エラー行が1件でもある場合、取込は実行されない（修正して再アップロード）。
- 取込は **取込権限ロール**（Firebase カスタムクレーム `role=admin`）を持つ利用者のみ実行可能。
  権限のない利用者は参照のみ（詳細は `infra/README.md`）。

## デプロイ

GitHub Actions によるデプロイ（フロント→Firebase Hosting、API→AWS EC2）を構成済み。
通常運用は `deploy` ワークフロー（事前検証 → テストゲート[単体・結合・シナリオ] → バックエンド → フロントエンド → 結果レポート）を使用する。
テストが1つでも失敗するとデプロイは中断され、失敗内容は Step Summary とアーティファクト `deploy-logs` に記録される。
緊急時の個別デプロイは `deploy-backend` / `deploy-frontend` を使用する（テストゲートを迂回するフォールバック）。
初回セットアップとデプロイの全手順（PowerShell コマンドベース）は
`infra/deploy-guide.md` を参照。構成の概要は `infra/README.md`。
